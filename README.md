# Duckling V3 simulation

MuJoCo model, Simulink balance controller, and a ROS 2 SLAM + YOLO navigation stack for a small Microduck-based biped. Everything here runs in simulation; nothing has been validated on hardware yet.

**Credits and licenses.** The robot model is derived from Pollen Robotics' [microduck_rl](https://github.com/pollen-robotics/microduck_rl) (MJCF under Apache-2.0; meshes under CC BY-NC-SA 4.0, not included here: clone upstream and run `scripts/make_duck_v3.py`). The Simulink plant uses MathWorks' [mujoco-simulink-blockset](https://github.com/mathworks-robotics/mujoco-simulink-blockset) (BSD-3, patched as described below). Walking uses Pollen Robotics' pretrained policies from Hugging Face (`pollen-robotics/microduck-policies`, not included). YOLO training uses Ultralytics YOLOv8 (AGPL-3.0); trained weights are not included. Generated model XML is in `model/`; mesh files and copied upstream files are regenerated by the scripts.

Then, from `C:\dev\duckling_sim`:

```powershell
.\.venv\Scripts\python.exe scripts\inspect_model.py microduck_rl\src\mjlab_microduck\robot\microduck\scene_walk.xml
```

- `inspect_model.py` is the PDF's Part 2 printout: 14 servos (5 per leg, 4 in the neck/head), 0.737 kg upstream, timestep 0.002 s, keyframes INIT / STAND / SIT / FOLD.
- `make_duck_v3.py` copies the upstream model to `model\` and writes `duck_v3.xml`. **The block at the top of that file is the only place you edit**: weighed link masses, the V3 added parts, servo gains from your bench test. It also adds a push point with `push_x` / `push_y` force inputs (last two actuators), sensors with Simulink-safe names (`gyro`, `accel`, `quat`, `torso_pos`, `q_<joint>`), and a `sim_start` keyframe.
- `stand_numbers.py` measures the model in its STAND pose and writes `model\stand_numbers.json`, which MATLAB reads.

**The redesigned V3 head and rear shield are in the model.** `prep_v3_meshes.py` takes `duck_head_upper_v3.stl`, `duck_head_lower_v3.stl` and the shield from `Downloads\Duckling_V3_Design_and_MuJoCo\duckling_v3\modified`, cuts each head shell from about 400k to 20k triangles, converts millimetres to metres, and measures volumes. `make_duck_v3.py` then removes the upstream head shells and puts the V3 ones in their place. Run it once before `make_duck_v3.py`:

```powershell
.\.venv\Scripts\python.exe scripts\prep_v3_meshes.py
```

**Estimates you must replace with measurements** (top block of `make_duck_v3.py`):
- Head: the V3 shells have 20.5 cm³ more plastic than the originals, so the head gets +22.9 g (volume × PLA density × 0.9). Weigh the printed shells and type the values in.
- Rear shield: 29.1 g from its volume, placed 50 mm behind the torso origin. Both are guesses.
- V3 head position: front flush with the upstream face, bottom at the upstream shell's bottom. `HEAD_SHIFT` nudges it. Check against the real robot.
- All other link masses are upstream Microduck values. The servo model (kp 0.55 N·m/rad, 0.96 N·m limit) is upstream's Dynamixel XL330, not your Feetech.

Things that differed from the PDF:
- A `mass=` on an added geom is ignored, because every upstream body has an explicit `<inertial>`. The script adds each V3 part as a small welded child body instead.
- The walk model only collides at the feet. When the duck falls, the body passes through the floor; that is expected, and "fell" is detected from torso height.

## Part B: MATLAB + Simulink

One-time build of the blockset (downloads MuJoCo 3.3.6 and GLFW 3.3.7 into the blockset folder, then compiles 4 MEX files with MSVC):

```powershell
& "C:\Program Files\MATLAB\R2026b\bin\matlab.exe" -batch "run('C:/dev/duckling_sim/matlab/build_blockset.m')"
```

Why a custom build script: release 4.x of the blockset ships no prebuilt `.mltbx`, and its own `build` needs `gmake`. `build_blockset.m` runs the repo's `install` and then calls `mex` directly.

The one source patch (already applied in `mujoco-simulink-blockset\src\mj.cpp`, function `initData`): the plant block always started from the model's zero pose, with straight legs. Three lines make it start from a keyframe named `sim_start` if the model has one. If you re-clone the blockset, re-add:

```cpp
int simStartKey = mj_name2id(m, mjOBJ_KEY, "sim_start");
if(simStartKey >= 0) mj_resetDataKeyframe(m, d, simStartKey);
```

Then in MATLAB:

```matlab
cd C:\dev\duckling_sim\matlab
startup_duck        % paths; run first in every session
duck_numbers        % PDF Part 4 hand calculations + PD and LQR gains
build_duck_sim      % creates duck_sim.slx from scratch (PDF Parts 6 and 7)
open_system('duck_sim')   % press Run: a MuJoCo window shows the duck balancing
run_tests           % PDF Part 8, all six tests, about 4 minutes
```

To push the duck by hand: set `push_F = 3` (newtons, forward, 0.05 s at t = 1 s) in the workspace and run. `balance_on = 0` turns the loop off.

What `duck_sim.slx` contains: MuJoCo Plant (0.002 s) → Bus Selector → Rate Transitions → `Controller` (atomic, 0.01 s) → optional `Extra delay` → Rate Transition → Mux with the push inputs → Plant. Inside `Controller`: the `tiltFilter` MATLAB Function block (complementary filter, α = 0.980), gains `K_TH` and `K_D`, ±0.25 rad saturation, added to the left ankle and subtracted from the right (the right leg's joints are mirrored).

Two blockset gotchas the script handles:
- Set the plant's XML through the parameter `xmlFileRel`. Setting the hidden `xmlFile` directly gets overwritten by `dummy.xml` at the next model update.
- Switching the XML several times in one session can crash the blockset's bus parser. `clear mj_initbus` before each switch avoids it.

| Needed bandwidth / loop rate | 2.9 Hz / 58 Hz (controller runs at 100 Hz) |

### Test results (Simulink controller + MuJoCo plant)

| # | Test | Result | Prediction |
|-|-|-|-|
| 1 | Hold pose, loop off, 10 s | Tips over at 1.05 s. Knee sag 5.5° | "Stands or tips slowly"; sag 7.0° by hand |
| 2 | Stand, loop on, 60 s | Stands. Pitch steady at +1.71°, moving ±0.47° | Within ±1° |
| 3 | Push 2 N × 0.05 s (0.10 N·s) | Stands. Peak 2.2°, back within 1° after 0.27 s | Recovers within about 1 s |
| 4 | Push limit, forward | Survives 5.0 N, falls at 5.5 N (0.250 to 0.275 N·s) | 0.219 N·s |
| 4 | Push limit, backward | Survives 2.0 N, falls at 2.5 N (0.100 to 0.125 N·s) | 0.106 N·s |
| 5 | Extra delay of 1, 2, 3 samples, 2 N push | Stands at all three (peak 2.4°, 2.6°, 2.7°) | Stands at 1, degrades by 3 |
| 6 | Torso mass +10% / −10% | Stands, and survives the 2 N push, both ways | Still passes |

All six pass with the retuned gains.

**The retune.** The PDF's rule (bandwidth 2·p, damping 0.7) gives 4.21·pitch + 0.260·rate. With those gains test 5 failed at every delay: one extra 10 ms sample and a 2 N push started a growing oscillation and the duck fell backward about 4 s later. `scripts\tune_gains.py` sweeps the two gains against 0 to 4 extra samples of delay and pushes in both directions:

```powershell
.\.venv\Scripts\python.exe scripts\tune_gains.py
```

Every pair with `K_TH` between 1.5 and 2.5 survives all of it; at 3.0 it needs `K_D` of 0.15 or more; from 3.5 up it starts falling at the larger delays, and 4.21 fails at 2 or more extra samples. I set the top of the safe band, `K_TH = 2.5`, `K_D = 0.20`. In `duck_numbers.m` that is `BW_FACTOR = 1.4` (bandwidth 1.4·p instead of 2·p) and `ZETA = 0.77`. The cost: the standing lean goes from 0.7° to 1.7° and the forward push limit drops from 5.5 N to 5.0 N; the backward limit improves from 1.5 N to 2.0 N. The ROS node and `push_test.py` use the same new defaults.

**What was tuned.**
- *Walk command.* The policy stands still below a command of about 0.2. 0.3 walks.
- *Obstacles.* At 0.3 the duck stalls on the 5 mm plank. `scripts\tune_obstacles.py` sweeps the walk command and servo stiffness: command 0.5 at the upstream stiffness clears all five planks; doubling the stiffness makes it worse. With taller planks it clears 20 mm and stops or falls at 25 mm.
- *Dance.* There is no dance policy. The routine in `m_dance` is choreography I wrote on top of the velstand policy's own command inputs (body roll and pitch, body height, four head joints, turn rate), on a 120 bpm beat. Edit the `choreo` function to change it.

**Caveats.** The policies were trained for the upstream Microduck with the BAM XL330 servo model; here they drive the V3 masses through the model's simple PD servos. They tolerate the V3 head and shield as modelled, which is the "walks as before" outcome in the PDF's Part 9 table. That result holds only as far as the estimated masses do, and says nothing yet about your Feetech servos.

## Part E: SLAM navigation with the head camera and depth

`scripts\slam_nav.py` puts the duck in a 4.4 × 3.2 m room it has never seen (two partition walls forming an S-shaped route, three boxes) and asks it to reach a magenta beacon it cannot see from the start.

```powershell
.\.venv\Scripts\python.exe scripts\slam_nav.py --gif
```

Add `--view` to watch, `--no-match` to switch scan matching off.

Sensors the algorithm uses: head camera RGB and depth (160 × 120, both rendered from one MuJoCo camera at the upstream camera position), gyro z, and the camera's pose relative to a level body frame (servo encoders plus IMU roll and pitch). Position and heading come only from the SLAM; MuJoCo's true pose is used for scoring.

The algorithm, written for this project:

1. **Predict.** Heading from gyro z; position from the calibrated walking speed along that heading. 50 Hz.
2. **Scan.** Depth image → 3-D points → keep those 3 to 30 cm above the floor → nearest hit per 2° of bearing. Floor-only directions count as free space.
3. **Match.** Try a small window of shifts (±7.5 cm, ±6°) around the prediction and keep the one whose scan endpoints land best on a blurred copy of the map. Move 60% of the way there.
4. **Map.** Log-odds occupancy grid, 2.5 cm cells: free along each ray, occupied at hits.
5. **Find the goal.** Magenta pixels in the RGB image, their depth, and the current pose give the beacon's map position (running mean).
6. **Plan.** Breadth-first wavefront over free space kept 12.5 cm from obstacles: to the beacon if known, otherwise to the nearest frontier (free cell next to unknown). 1 Hz.
7. **Drive.** Pure pursuit of the path as a twist command to the walking policy. The head sweeps left and right so the 75° camera covers about 190°.

| | With scan matching | Without (dead reckoning) |
|-|-|-|
| Outcome | Reached the beacon | Reached the beacon |
| Time | 48 s | 45 s |
| Stopped this far from the beacon | 0.34 m | 0.41 m |
| Position error, mean / max | 5.3 cm / 11.6 cm | 6.1 cm / 13.3 cm |
| Beacon position error | 15 cm | 9 cm |
| Path walked, falls | 6.3 m, 0 | 6.8 m, 0 |

Outputs in `results\slam\`: `map.png` (map, true path in green, estimated path in red), `slam.gif` (the map growing), `camera_rgb_depth.png` (one camera frame), `summary.txt`.

**What this does and does not show.**
- Scan matching helps only a little here. Over a 6 m route with a perfect simulated gyro and a calibrated walking speed, dead reckoning alone is already within 6 cm. The correction matters on longer routes and with real gyro drift, which this run does not test.
- One room, one start, one run each. No loop closure: the map is never re-aligned after the fact.
- The depth image is ideal (no noise, no holes), and the camera's height and tilt are taken as known exactly.
- It is a 2-D map from a 3-D sensor. Anything lower than 3 cm is treated as floor.
- This script runs in Python next to MuJoCo. Part F is the same algorithm as ROS 2 nodes, with YOLO added.

## Part F: SLAM + YOLO as ROS 2 nodes, duck walking around a room

The package `ros2\duck_nav` runs the whole thing as six ROS 2 nodes in WSL. The duck starts in a 5.2 × 4 m room with three partition walls, five boxes and two 8 mm planks on the floor, explores it, walks to the beacon when YOLO finds it, then finishes exploring.

| Node | Job | Main topics |
|-|-|-|
| `world_sim` | MuJoCo room + duck + walking policy. Stands in for the robot and its sensors | in: `/cmd_vel`, `/head_yaw_cmd`. out: `/clock`, `/joint_states`, `/imu`, `/camera/image_raw`, `/camera/depth`, `/camera/pose_level` |
| `yolo_node` | YOLOv8-nano on the camera image (ONNX Runtime, CPU) | in: `/camera/image_raw`. out: `/yolo/detections`, `/yolo/image` |
| `slam_node` | DuckSLAM: predict, depth scan, scan matching, grid map; beacon position from YOLO boxes + depth | out: `/map`, `/slam/pose`, `/goal`, TF `map → base_level` |
| `nav_node` | Frontier exploration, path planning, pure pursuit, head sweep | in: `/map`, `/slam/pose`, `/goal`. out: `/cmd_vel`, `/plan`, `/nav/status` |
| `score_node` | Referee: compares SLAM with MuJoCo's true pose, writes the summary. Feeds nothing back | out: `summary.txt`, `map.png` |
| `robot_state_publisher` | Draws the duck in RViz from the URDF | |

### YOLO: how the detector was made

A COCO-pretrained YOLO does not know what a beacon or a plain box in MuJoCo looks like, so I fine-tuned YOLOv8-nano on rendered images. MuJoCo's segmentation render gives the labels for free.

```powershell
.\.venv\Scripts\python.exe -m pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe -m pip install ultralytics onnx onnxslim
.\.venv\Scripts\python.exe scripts\worldgen.py
.\.venv\Scripts\python.exe scripts\yolo_dataset.py
.\.venv\Scripts\python.exe scripts\yolo_train.py
```

- `worldgen.py` writes the demo room (`model\duck_v3_gc_world.xml`) and makes random rooms for training.
- `yolo_dataset.py` renders 580 head-camera images from 45 random rooms, two classes: `beacon` and `box`. Pink and purple boxes are included as distractors.
- `yolo_train.py` trains 30 epochs on the CPU (about 13 minutes) and exports `yolo\duck_yolo.onnx`.
- On 72 held-out renders: beacon mAP50 0.995, box mAP50 0.954 (recall 0.90). These are synthetic images from the same generator, so this says nothing about real camera photos.

Ultralytics YOLO is AGPL-3.0 licensed, which matters only if you distribute a product built on it.

### Things to know

- **RViz map display not confirmed.** RViz started and stayed up, but logged one shader error (`indexed_8bit_image.vert`), which is the shader the Map display uses. I did not look at the window, so the map may not draw. If it is blank, start RViz with software rendering: `LIBGL_ALWAYS_SOFTWARE=1 ros2 launch duck_nav duck_nav.launch.py`.
- **The map is slightly skewed** (walls lean by about 3°) and the position error is larger than in the standalone script. Heading drift is not fully corrected; there is still no loop closure.
- **The camera does not see the duck's own body.** Its meshes are hidden in the camera render to keep rendering fast in WSL (150 ms with them, 28 ms without).
- **Planks are invisible to the map on purpose.** Anything under 3 cm counts as floor, and the walking policy steps over the 8 mm planks.
- **`/camera/pose_level` and the body tilt are exact.** They stand for what neck encoders and the IMU would report; on a robot they will carry error.
- **Falls wreck the position estimate.** In two later re-check runs, one was clean (beacon at 49 s, 5 cm mean error, no falls) and one was poor: the duck fell three times, the SLAM error grew to 55 cm mean (99 cm max) and the beacon estimate was 0.86 m off, although it still got within 0.17 m of the real beacon and finished at 144 s. While the duck tumbles, gyro z is no longer the heading rate and nothing corrects the error afterwards. Fixing that (freeze the heading while not upright, then re-localise against the map) is the first improvement to make.
- Four runs in one room in total: three good, one poor. No other layouts tried. `results
os2_nav\summary.txt` and `map.png` now hold the latest re-check run, not run 1.

- **Retraining the walking policy** on your measured masses and Feetech servo model: needs an NVIDIA GPU (yours is AMD) or a rented one. The pretrained policies run as-is in Part D.
- **Anything on the UNO Q**: see `Duckling_V3_UNO_Q_Guide.md` for the step-by-step plan.
